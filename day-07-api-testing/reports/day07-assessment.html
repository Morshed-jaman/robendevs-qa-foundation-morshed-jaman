## Methodology and limitations

- POS-15 is saved as an empty-URL GET with no assertions despite its Delete Test User name. It was preserved; it cannot delete the user.
- NEG-03 uses username robendevs_qa_20261116_81; create/update use robendevs_qa_20261116_814. A passing 404 cannot prove deletion of the created user.
- No saved updated-user verification exists. POS-13 verifies pre-update values and cannot be moved after update without changing its assertions.
- Saved source has 52 assertions; the historical run also had 52. No source request UUIDs exist; names and case IDs were preserved. Generated SDK IDs are not recovered original IDs.
- Export preserves folders; execution uses an in-memory flattened order to interleave deletion checks. No original assertions, request methods, URLs, headers or bodies were changed.
- This is a custom explicit YAML mapping validated against the official v2.1 JSON schema and loaded by the Postman SDK. It is not a native Postman export or official v3 downgrade utility.
- Shared demo data and fixed IDs can interfere with results. No retries or additional cleanup requests were added; created user and NEG-06 pet may remain.
- Only public demo credential fixtures were retained. Returned cookies/session material is redacted in saved JSON/HTML. No private environment was exported.
- Historical and current discrepancies need contract investigation; they are not automatically confirmed bugs or security vulnerabilities.

## Contract discrepancies, conclusion and recommendations

The [captured Swagger contract](reports/petstore-swagger-contract.json) documents 400 for invalid pet IDs and invalid status values; Pet requires name and photoUrls. Inventory declares api_key security, but its response definitions do not specify 401/403. Login documents 400 for invalid credentials. Order retrieval documents IDs 1–10, while the saved test uses 2026111609: this is a test-data contract limitation even though the request passed. See https://petstore.swagger.io/v2/swagger.json. Missing-name acceptance warrants required-field validation investigation; invalid-status acceptance warrants enum validation review; invalid-ID status warrants error-contract review. Authentication behavior on a public demonstration service needs confirmation of intended enforcement. No finding here is automatically a confirmed vulnerability.

The evidence cannot establish complete user CRUD coverage. Repair POS-15, align NEG-03 username, and add a separate updated-user verification in a reviewed revision. Keep existing assertions intact until the contract is agreed. Re-run with isolated test data after repair. Inspect request failures separately from assertion failures.
